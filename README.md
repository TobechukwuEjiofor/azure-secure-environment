# Secure Azure Environment with Terraform

A three-tier Azure environment built entirely as code: a private network, a bastion, an app server with no public IP, a load balancer, a private PostgreSQL database, secrets in Key Vault, and Terraform state stored remotely. Nothing was created in the Azure portal.

## The scenario (fictional)

**Bridgeline Pay**, a small fintech, has an Azure environment that a contractor built by clicking through the portal: a public app server with SSH open to the internet, a database firewall with a forgotten home IP, a database password pinned in a team chat, and no record of what was clicked. A partner bank sends a security questionnaire the company cannot answer. This project rebuilds the environment properly and answers each question with evidence.

## Architecture

```
                 Internet
                    |
          [ Public Load Balancer ]   <- the only public entry point (HTTP)
                    |
  ----------- Virtual Network 10.0.0.0/16 ------------------
  |                                                         |
  |  Public subnet            Private subnet                |
  |  [ Bastion VM ] --SSH-->  [ App VM ]                    |
  |   (admin IP only)          (no public IP)               |
  |                                |                        |
  |                         Database subnet                 |
  |                         [ PostgreSQL 16 ]               |
  |                          (no public access)             |
  -----------------------------------------------------------

  Key Vault ........ holds the generated database password
  Storage account .. holds Terraform's remote state (separate resource group)
```

34 resources in total, all tagged with project, environment and owner.

## The bank's five questions

| Question | Answer | Evidence |
|---|---|---|
| 1. Is the database reachable from the internet? | No. Public network access is disabled and the server has a private address only. | Azure shows `publicNetworkAccess: Disabled`. The server name does not resolve from outside the network. Port 5432 is open from the app VM and closed from the bastion. |
| 2. Who can log in, and from where? | One admin IP, to the bastion only. The app VM has no public IP and accepts SSH only from the bastion subnet. | NSG rules, an empty public IP list on the app VM, and a direct SSH attempt that times out. |
| 3. Where are secrets stored? | In Key Vault. The password is generated by Terraform, never typed, and never committed. The app VM reads it through a managed identity. | The VM fetched the secret with no stored credential and logged in to the database with it. A search of every git commit found the password nowhere. |
| 4. Can you rebuild from scratch? | Yes. | All 34 resources were destroyed, then rebuilt from a fresh clone of this repository, then destroyed again. |
| 5. Where is the state stored, and who can change it? | In an Azure storage account with locking and versioning, no public blob access, and a firewall that allows only the admin IP. | The state blob is in Azure with no local state file. The lock is taken and released on every run. |

## Design decisions

**1. How does a private VM reach the internet?** The private subnet has default outbound access switched off, so the VM has no hidden way out. The load balancer provides an explicit outbound rule instead, so every outbound connection leaves from one known address. The VM's first boot waits for that rule, because it installs nginx on startup.

**2. How does a VM read a secret with no password?** The app VM has a system-assigned managed identity with the "Key Vault Secrets User" role, which can read secrets and nothing else. The Key Vault firewall denies by default and allows the admin IP (so Terraform can write the secret) and the private subnet (so the VM can read it).

**3. The password is in Key Vault, but is it also in the state file?** Yes. Terraform records generated values in state. The password is not in git, and the state storage is private, versioned, locked and firewalled, but it is present. Anyone who can read the state can read the password.

**4. How is the database made private?** The database subnet is delegated to PostgreSQL flexible servers, the server has no public endpoint, and a private DNS zone linked to the virtual network resolves its name. The database NSG allows port 5432 from the app subnet only and ends with an explicit deny-all, which overrides Azure's default rule that lets every subnet talk to every other.

## Trade-offs and limitations

- **Allow-lists tied to one IP.** The state storage firewall, the Key Vault firewall and the bastion rule all depend on the admin's public IP, which changes. Each needs updating when it does. A VPN with a fixed address would fix this.
- **No HTTPS or domain.** The load balancer serves plain HTTP on port 80.
- **Single instances.** One app VM and one database, with no redundancy.
- **Key Vault has a public endpoint behind a firewall.** A private endpoint would remove it entirely, at extra cost and complexity.
- **Shared-key access is still enabled** on the state storage account. Switching Terraform to Azure AD authentication would remove it.
- **The bootstrap step is outside the main configuration.** The state storage account has to exist before Terraform can use it, so it is created by a separate configuration in `bootstrap/` with local state. This is the one documented exception to "everything in one place".
- **`psql` was installed by hand** on the app VM for the login test. It is not part of the environment.

## Repository layout

```
bootstrap/   creates the state storage account (run once, local state)
infra/       the environment
  network.tf        virtual network, subnets
  nsg.tf            security groups and subnet associations
  bastion.tf        bastion VM and public IP
  app.tf            private app VM with managed identity
  loadbalancer.tf   public IP, load balancer, probe, rules
  database.tf       private PostgreSQL, DNS zone, generated password
  keyvault.tf       vault, role assignments, secret
  evidence.sh       prints the proof for each acceptance test
```

## How to deploy

Requirements: Azure CLI (logged in), Terraform 1.5 or later, and an RSA SSH key at `~/.ssh/azsecure_key.pub` (Azure rejected Ed25519 keys for these VMs).

1. **Create the state storage:** in `bootstrap/`, create `terraform.tfvars` with `allowed_ip = "YOUR.PUBLIC.IP"`, then run `terraform init` and `terraform apply`.
2. **Point the backend at it:** copy the storage account name from the output into the `backend "azurerm"` block in `infra/providers.tf`.
3. **Build the environment:** in `infra/`, create `terraform.tfvars` with `admin_cidr = "YOUR.PUBLIC.IP/32"`, then run `terraform init`, `terraform plan -out=plan.tfplan` and `terraform apply plan.tfplan`.
4. **Collect the evidence:** `bash evidence.sh`
5. **Tear down:** `terraform destroy` in `infra/`. Do not destroy `bootstrap/` unless you are finished with the project, because it holds the state.

`*.tfvars`, `*.tfstate` and `*.tfplan` are git-ignored. VM sizes and regions vary by subscription. `uksouth` with `Standard_D2s_v3` worked on mine.

The VMs, load balancer, database and public IPs bill by the hour, so destroy the environment when you finish testing.

## What I learned

- **A dropped connection can look like a project bug.** Intermittent failures to Azure's management endpoint caused errors across many unrelated resources. Measuring the failure rate and switching network fixed it, and no Terraform change did.
- **A stuck state lock is safe to clear once you check why.** A failed plan could not release the lock. I confirmed that the lock belonged to me, that it was a read-only operation, and that nothing else was running before I force-unlocked it.
- **Some changes force replacement.** Turning off default outbound access on an existing subnet replaced the subnet. It was safe only because nothing lived in it yet.
- **Azure changes things behind Terraform's back.** Creating the database added a storage service endpoint to its subnet, and Terraform wanted to remove it. I declared it in code to match.
- **Order matters for identities.** Adding a managed identity to an already-running VM and using its ID in a role assignment in the same plan failed with a missing `principal_id`. Applying the identity first resolved it.
- **Read the plan before every apply.** Twice the plan showed something I had not predicted, and checking it first avoided a mistake.
